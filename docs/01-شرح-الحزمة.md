## الفكرة بجملة وحدة

قبل ما تكتب أي فيتشر (طلبات، قائمة، دفع)، لازم يكون في **أساس** — قاعدة بيانات، وقفل أمان، وطريقة تشغيل موحّدة عند الخمسة. هالحزمة **هي الأساس**، جاهز ومختبَر. Sprint 0 مهمته الوحيدة إنك تركّبه وتشغّله.

**كله اتشغّل فعليا على PostgreSQL 16 قبل ما ينوصل لإيدك.** مش مقترحات ولا كود من راسي — كل سطر انفّذ وطلعت نتيجته.

# 1️⃣ مجلد `db/` — بناء قاعدة البيانات

### `db/migrations/` — ثلاث ملفات، بتنفّذ بالترتيب

**"Migration" يعني:** ملف بيقول لقاعدة البيانات "اعملي هالجدول، وضيفي هالعمود". بدل ما كل واحد بالفريق يعمل الجداول بإيده (وبتطلع مختلفة عند كل واحد) — بنكتبها مرة، والكل بيشغّل نفس الملفات، فقاعدة البيانات بتطلع **متطابقة حرفيا** عند الخمسة وعلى السيرفر.

| الملف | شو بيعمل | ليش يهمك |
|---|---|---|
| `0001_enums_and_tables.sql` | بيعمل **١٣ جدول** + قواعد سلامة | هيك بتخزن البيانات |
| `0002_indexes.sql` | **١٩ فهرس** | بدونهم كل شي بيصير بطيء لما تكبر البيانات |
| `0003_roles_and_rls.sql` | **قفل الأمان** | 🔴 أخطر ملف بالمشروع |

#### شو يعني "فهرس" (Index)؟

زي فهرس آخر الكتاب. بدونه، لما تدوّر على كلمة، بتقلّب الكتاب صفحة صفحة. معه، بتفتح الفهرس وبتروح مباشرة.

قاعدة البيانات نفس الشي: بدون فهرس على "الطلبات المفتوحة"، لما اللوحة تسأل عنها كل ٤ ثواني، القاعدة بتقرأ **كل الطلبات من أول المشروع** كل مرة. مع مطعم عنده ١٠٠ طلب مش مشكلة. مع ١٠,٠٠٠ طلب، اللوحة بتوقف.

كل فهرس بالملف **مربوط باستعلام حقيقي** موجود بمخططات البلوبرينت. ولا واحد "احتياطي".

#### 🔴 شو يعني RLS؟ (أهم مفهوم بالملف كله)

**المشكلة:** عندك مطعمين على نفس النظام — "شاورما الأصيل" و"مطعم النور". بيانات الاثنين بنفس الجداول. **شو بيمنع أن مطعم يشوف زبائن التاني؟**

**الجواب التقليدي:** المبرمج بيكتب بكل استعلام `WHERE restaurant_id = ?`.

**ليش هذا خطر:** إنت عندك عشرات الاستعلامات. **بكفّي واحد بس ينساها** → مطعم بيشوف زبائن غيره. وهاي مش بتظهر بالاختبارات، بتظهر لما زبون يشتكي.

**RLS (Row-Level Security)** بيقلب المعادلة: قاعدة البيانات نفسها بترفض تعطيك صفوف مطعم تاني، **حتى لو المبرمج نسي الشرط**. مش أن الاستعلام بيرجع خطأ — بيرجع **صفر صفوف**. الأمان صار قاعدة بالقاعدة، مش انضباط بشري.

**الحالة الأخطر — اللي هالمشروع اتصمّم عشانها:**
مطعم عنده فرعين. "أحمد" مدير عند الفرعين — يعني **مصرّح له بالاثنين فعليا**. لما يفتح لوحة فرع الشميساني، لازم يشوف الشميساني **بس**. `WHERE restaurant_id = ?` بيمرّ هون بالصدفة. بينساها المبرمج → أحمد بيشوف الفرعين مخلوطين وبيقبل طلب من الفرع الغلط.

**كيف بيشتغل عمليا:**

```
1. أحمد بيسجّل دخول            → منعرف مين هو
2. بيفتح لوحة فرع الشميساني    → منسأل: "أحمد عضو فعّال بالشميساني؟"
3. الجواب نعم                  → منقول للقاعدة "هالطلب كله للشميساني"
4. من هون لآخر الطلب           → القاعدة بترفض أي صف مش للشميساني
```

الترتيب مقدّس. لو عملت ٣ قبل ٢، يعني خلّيت **المستخدم يختار وين بدّه يوصل** والقاعدة بتوصّله بأمانة. RLS بيحصر الطلب بمطعم واحد؛ **مين هو هالمطعم — هاد قرار الـGuard**.

### `db/seed/chain-isolation-fixture.sql`

بيانات وهمية للاختبار: سلسلة بفرعين + موظف عضو بالاثنين + مطعم تالت غير مرتبط. **للتطوير والاختبار بس. أبدا على الإنتاج.**

# 2️⃣ مجلد `tests/` — الفحوصات اللي بتمنع الكوارث

### 🔴 `tests/security/chain-isolation.sql` — بوابة Sprint 0 الإلزامية

**١٢ فحص.** كل واحد بيحاول يخترق العزل بطريقة، ولازم يفشل:

| # | بيحاول | لازم يصير |
|---|---|---|
| A1 | يقرأ بدون ما يحدد مطعم | صفر صفوف — النظام **بيفشل مقفول** مش مفتوح |
| A2 | 🔴 موظف بفرعين، بيشوف الفرع التاني | الفرع الشقيق **غير مرئي تماما** |
| A3 | يبدّل للفرع التاني | بيشوف التاني بس، مش الأول |
| A4 | 🔴 يقرأ بعد ما خلص الطلب السابق (تسريب الـpool) | صفر صفوف |
| A5 | يكتب صف بمطعم تاني | مرفوض |
| A6 | ينقل صف موجود لمطعم تاني | مرفوض |
| A7 | يمسح صفوف مطعم تاني | صفر صفوف تأثرت |
| A8 | يقرأ أصناف طلبات مطعم تاني | مرفوض |
| A9 | يزوّر رقم مطعم غير موجود | صفر صفوف |
| A10 | يبعت رقم فاضي (يمكن يصير wildcard؟) | صفر صفوف |
| A11 | يتجاوز فحص العضوية | مرفوض |
| A12 | يستخدم عضوية موقوفة | مرفوض |

**A4 يستاهل شرح** — لأنها ثغرة ما بتظهر بأي اختبار عادي:

السيرفر ما بيفتح اتصال جديد بقاعدة البيانات مع كل طلب (بطيء كتير). بيحتفظ بمجموعة اتصالات جاهزة ("connection pool") وبيعيد استخدامها. **إذا كتبت "المطعم الحالي" على الاتصال بشكل دائم بدل مؤقت** — الطلب الجاي اللي بياخد نفس الاتصال بيرث مطعم الطلب اللي قبله. **مطعم بيقرأ بيانات مطعم تاني.** وهاي ما بتظهر أبدا وإنت لحالك عالجهاز؛ بتظهر أول ما يصير مطعمين شغالين بنفس الوقت.

### `tests/security/negative-controls.sh` — الاختبار اللي بيختبر الاختبار

> **اختبار أمني ما شفته وهو بيفشل، هو `assert(true)` بلبس مختلف.**

هالسكريبت **بيكسر الأمان عمدا بثلاث طرق** وبيتأكد إن الفحص فوق **بيحمرّ** بكل وحدة:

1. **يطفي RLS على جدول** — بيصير لما migration مستقبلية تعيد إنشاء جدول وتنسى تفعّلها
2. 🔴 **يخلي مستخدم التطبيق superuser** — **أخطر وحدة**: superuser بيتجاوز كل سياسات RLS، **بدون ولا رسالة خطأ**. وهاد بالضبط الـconnection string اللي Railway/Neon/Supabase بيعطوك إياه افتراضيا. تلزقه بالـ`.env` → كل أمانك انطفى وإنت مش دارِي
3. **يخلي السياق دائم بدل مؤقت** — تسريب الـpool اللي شرحناه فوق

عشان الحالة ٢، `TenantDbService` **بيرفض يشغّل التطبيق أصلا** لو الـ`DATABASE_URL` superuser. تخريب مقصود، أحسن من اختراق صامت.

### `tests/db/critical-primitives.verify.ts`

بيثبت إن أربع عمليات بتشتغل صح فعلا. شرحها بالقسم ٤ تحت.

### `tests/db/schema-drift.verify.ts`

عنا **نسختين** من وصف الجداول: SQL (اللي بيبني القاعدة) و TypeScript (اللي الكود بيقرأ منها). لو حدا عدّل وحدة ونسي التانية، الكود بيتوقّع عمود مش موجود → انفجار وقت التشغيل. هالفحص بيقارنهم **عمود بعمود** ويطلع أحمر فورا.

# 3️⃣ `packages/shared/` — الكود المشترك

**المشكلة:** الباك اند بيعرف إن حالات الطلب سبعة. الفرونت اند لازم يعرف نفس السبعة. لو كل واحد كتبها عنده، أول ما تضيف حالة تامنة بتنسى تعدّل الفرونت.

**الحل:** تنكتب **مرة وحدة** هون، والاثنين بيستوردوها. تعدّل هون → الفرونت اند **ما بيبني** لحد ما ينعدّل. الخطأ بيمسك وقت الكتابة مش وقت التشغيل.

- `schema.ts` — وصف الجداول بلغة TypeScript
- `domain.ts` — الحالات، النصوص العربية، **والانتقالات المسموحة**

مثال من `domain.ts`:

```ts
// طلب أونلاين ما بينقبل قبل تأكيد الدفع (FR-13)
canAcceptOrder({ paymentMethod: 'online', paymentStatus: 'pending_online' })  // false
```

الباك اند بيستخدمها ليرفض الطلب، والفرونت اند بيستخدمها ليعطّل الزر. **نفس السطر.** مستحيل يختلفوا.

# 4️⃣ `apps/` — الخدمات

### `apps/conversation-engine/src/db/critical-primitives.ts`

**أربع عمليات، كل صحة النظام معلقة فيهم.** إذا انكسر واحد، النتيجة فلوس ضايعة:

| العملية | المشكلة اللي بتحلها | لو انكسرت |
|---|---|---|
| **بوابة التكرار** | ميتا بتعيد إرسال نفس الرسالة أحيانا | 🔴 **طلبين بدل واحد** |
| **CAS** | الزبون ضغط "تأكيد" مرتين بسرعة | 🔴 **طلبين بدل واحد** |
| **قفل الصف** | الموظف بيلغي بنفس اللحظة اللي وصل فيها الدفع | 🔴 **استرجاع مرتين — المطعم بيدفع للزبون ضعف المبلغ** |
| **SKIP LOCKED** | نسختين من الـscheduler شغالين | 🔴 **نفس الطلب بينعالج مرتين** |

**ليش "بوابة التكرار" و"CAS" الاثنين؟ مش نفس الشي؟** لأ، ومهم تفهم الفرق:

- ميتا أعادت إرسال **نفس الرسالة** (نفس المعرّف) → **بوابة التكرار** بتمسكها
- الزبون ضغط "تأكيد" **مرتين** → هدول **رسالتين مختلفتين** بمعرّفين مختلفين. بوابة التكرار بتمررهم الاثنين (وهاد صحيح!) → **CAS** بتمسكها

كل وحدة بتغطي ثغرة التانية ما بتشوفها. **شيل أي وحدة، بترجع ثغرة "طلب مكرر" من باب تاني.**

### `apps/dashboard-api/src/db/tenant-db.service.ts`

**الطريق الوحيد المسموح للوصول لبيانات المطاعم.** الاتصال المباشر بالقاعدة `private` عمدا — لو خدمة قدرت توصله، فيها تعمل استعلام بدون تحديد مطعم.

### `apps/dashboard-api/src/auth/restaurant-context.guard.ts`

الـ٣٠ سطر اللي بتقرر إذا الطلب مسموح. بترتيب: **مين إنت؟ → مصرّح لك هون؟ → هلق شوف.**

## خلاصة: ليش هالحزمة موجودة أصلا؟

لأن **٣ أشياء لو انبنوا غلط، ما بتنصلح إلا بإعادة بناء**:

1. **العزل بين المطاعم** — لو بنيت ٢٠ فيتشر فوق guard مكسور، تصليحه يعني مراجعة الـ٢٠ كلهم
2. **منع الطلبات المكررة** — لو اكتشفتها بالبايلوت، يعني اكتشفتها من زبون بيصرخ
3. **تطابق البيئات** — لو Postgres مختلف عند كل واحد، رح تصرفوا أسبوع على "بشتغل عندي"

الثلاثة محلولين ومختبَرين. **هدف Sprint 0 إنك تركّبهم، مش تبنيهم.**
