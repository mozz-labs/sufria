## 2. القرارات — مقفولة

### 2.1 · رقم الطلب — 22 سبتمبر

**من التجربة الحقيقية:** رسالة التأكيد بلا رقم. الزبون يصل المطعم فماذا يقول؟ والموظف يبحث بماذا؟

- **رقم لكل مطعم، متسلسل، لا يُصفَّر، يبدأ من 101.** أول طلب في مطعم جديد رقمه 101. (من 101 لا من 1: أول زبون لا يرى «طلب رقم 1».)
- **العمود:** `orders.order_number integer NOT NULL`، و`UNIQUE (restaurant_id, order_number)`.
- **التخصيص داخل ترانزاكشن الإنشاء نفسها** (`12-after-cart-brief.md` §8، بين الخطوتين 2 و3):

  ```sql
  SELECT pg_advisory_xact_lock($ns, hashtext($restaurant_id::text));
  SELECT COALESCE(MAX(order_number), 100) + 1 FROM orders WHERE restaurant_id = $restaurant_id;
  ```

  `$ns` ثابت مسمّى في الكود لهذا القفل وحده. القفل يسلسل إنشاء الطلبات **لنفس المطعم** ويتحرّر عند الـCOMMIT. والقيد `UNIQUE` شبكة الأمان.
- **لماذا لا عدّاد في `restaurants`:** يحتاج UPDATE على `restaurants` من سياق المحرّك، وسياسات RLS ليست لنا لنغيّرها. **ولماذا لا تصفير يومي:** يحتاج حدّ يوم المطعم، ويجعل السجل ملتبسا.
- **النص:** `استلمنا طلبك رقم {رقم الطلب} — التأكيد خلال دقائق.` بأرقام غربية (الحارس القائم يمسك غيرها).
- **الهجرة تملأ الطلبات الموجودة** برقم لكل مطعم بترتيب `created_at` ثم `id`، بدءا من 101، ثم `NOT NULL` ثم القيود. إن منعت RLS الملء في سياق الهجرة، **قف**.

### 2.2 · العملة إعداد للمطعم — 22 سبتمبر

**المشكلة:** «د.أ» ثابتة في النصوص، ومطعم البايلوت التشغيلي في غزة يبيع بالشيكل. **والأردن يبقى سوق الإطلاق.**

- **العمود:** `restaurants.currency text NOT NULL DEFAULT 'JOD' CHECK (currency IN ('JOD','ILS'))`.
- **التسميات في `shared`:** `JOD` ← `د.أ` · `ILS` ← `شيكل`.
- **منسّق المبالغ القائم يأخذ العملة باراميترا. لا منسّق ثانٍ.** كل نص فيه مبلغ يمرّر عملة المطعم.
- العملة تُقرأ مع بيانات المطعم التي يقرؤها المحرّك أصلا في كل رسالة. **بلا snapshot**: العملة لا تتغيّر أثناء محادثة.
- **الافتراضي `JOD` يُبقي الاختبارات القائمة خضراء كما هي.** اختبار سقط بسبب العملة = تمرير ناقص في الكود، لا اختبار يُعدَّل.
- **لا تُعدَّل من اللوحة.** تُضبط عند تهيئة المطعم.

### 2.3 · سعر المنيو بعملته — 22 سبتمبر

سطر المنيو اليوم: `شاورما دجاج — 2.50`، بينما السلّة `2.50 د.أ`. **سطر المنيو يمرّ بنفس المنسّق.**

### 2.4 · سطر الدفع — 22 سبتمبر

`الدفع نقدا عند الاستلام.` ← **`الدفع نقدا.`** في الملخّص، للاستلام والتوصيل.
**السبب:** في طلب الاستلام يأتي مباشرة بعد `الاستلام من المطعم`، فتتكرّر الكلمة.

### 2.5 · التبويبان والترتيب — مقفول من قبل

| `tab` | الحالات | الترتيب | الصفحات |
|---|---|---|---|
| `active` | `pending_acceptance` · `accepted` · `preparing` · `ready` | **الأقدم أولا** | بلا صفحات |
| `history` | `completed` · `cancelled` · `expired` | الأحدث أولا | 20 بالصفحة |

- **الأقدم أولا قرار منتج:** الموظف في الذروة يريد أن يرى العالق.
- الترتيب بـ`created_at` **ثم `id`** لكسر التعادل. بلا كاسر، طلبان بنفس اللحظة قد يظهران في صفحتين أو لا يظهران.

### 2.6 · الانتقالات — وما عداها مرفوض

| من | إلى |
|---|---|
| `pending_acceptance` | `accepted` · `cancelled` |
| `accepted` | `preparing` · `cancelled` |
| `preparing` | `ready` · `completed` · `cancelled` |
| `ready` | `completed` · `cancelled` |
| `completed` · `cancelled` · `expired` | **لا شيء — نهائية** |

- `ready` اختيارية: `preparing ← completed` مباشرة مسموح.
- `expired` و`pending_acceptance` **لا تكونان وجهة من الموظف أبدا.** `expired` يضعها النظام (غير مبنية، Sprint 2).
- 🔴 **قاعدة تشغيلية:** في طلب التوصيل، `ready` تعني «سلّمناه للسائق» (`12-after-cart-brief.md` §2.7). الـAPI لا يفرضها، والشاشة تسمّي الزر بها.

### 2.7 · الموظف يرسل الحالة التي رآها — 22 سبتمبر

الطلب: `{ "from": "accepted", "to": "preparing" }`، والـCAS: `WHERE id = $id AND status = $from`.

**لماذا لا يقرأ الخادم الحالة الحالية ويستعملها:** موظف رأى «معلّق» وضغط «إلغاء»، وفي الأثناء قبله زميله وبدأ التحضير. لو استعمل الخادم الحالة الحالية، **يُلغى طلب في المطبخ بناء على شاشة قديمة**. مع `from`: 409 ويرى الموظف الحالة الحقيقية.

### 2.8 · الإلغاء

- **الموظف وحده** من اللوحة. الزبون لا يلغي بعد الإنشاء في البايلوت إلا عبر رقم المطعم.
- `cancelled_by = 'staff'`. و`cancellationReason` **اختياري**: يُقصّ من الطرفين، والفارغ بعد القصّ = NULL، والحدّ 300 حرف، ويُخزَّن كما كتبه الموظف.
- `cancellationReason` مع وجهة غير `cancelled` ← 400.

### 2.9 · 404 لا 403

طلب أو صنف لمطعم آخر = **404**. لا نقول للمطعم الآخر إن الشيء موجود.

### 2.10 · نطاق المنيو والإعدادات — قرار محمد، 22 سبتمبر

- **أولا: توفّر الصنف وسعره** — يتغيّران يوميا. **ثم:** ساعات الدوام · رسوم التوصيل · رقم التواصل.
- **للقراءة فقط:** `offers_delivery` (فجوة `12-after-cart-brief.md` §13: مطعم يطفئ التوصيل وسط محادثة غير معالج) و`currency` (§2.2).
- **خارج د:** إضافة صنف · حذفه · التصنيفات · الصور. منيو مطعم البايلوت يُدخَل بسكربت تهيئة.
- **الصلاحيات:** أي موظف مسجّل للمطعم. الأدوار خارج البايلوت.

## 3. العقود

### 3.1 · `GET /orders?tab=active|history&page=N`

```json
{
  "orders": [
    {
      "id": "8f1c…",
      "orderNumber": 104,
      "status": "pending_acceptance",
      "fulfillmentType": "delivery",
      "total": "13.50",
      "itemCount": 3,
      "createdAt": "2026-09-21T09:15:00.000Z",
      "customer": { "name": "أحمد", "phone": "+9627…" }
    }
  ],
  "page": 1,
  "hasMore": false
}
```

- `tab` إلزامي. `page` عدد صحيح موجب يبدأ من 1. **يُتحقَّق منه كلما أُرسل** (`page=0` أو `page=x` ← 400 في التبويبين)، **وأثره ملغى مع `active`**: الرد دائما `page: 1` و`hasMore: false`.
- `hasMore` في `history`: اقرأ 21 وأرجع 20. **بلا `COUNT`.**
- **بلا أصناف وبلا تاريخ.** اللوحة تسأل هذا المسار كل 3-5 ثوان، فيبقى خفيفا.
- `itemCount` = عدد أسطر الطلب.
- `customer.name`: إن لم يكن في `customers` عمود اسم (الفحص 5) ← `null`، **ولا عمود جديد في د**.

### 3.2 · `GET /orders/:id`

```json
{
  "id": "8f1c…",
  "orderNumber": 104,
  "status": "preparing",
  "fulfillmentType": "delivery",
  "subtotal": "12.00",
  "deliveryFee": "1.50",
  "total": "13.50",
  "paymentMethod": "cash",
  "paymentStatus": "pending_cash",
  "deliveryAddress": "…",
  "cancellationReason": null,
  "createdAt": "…",
  "customer": { "name": "أحمد", "phone": "+9627…" },
  "items": [
    { "name": "شاورما دجاج", "quantity": 2, "unitPrice": "2.50", "lineTotal": "5.00" }
  ],
  "history": [
    { "from": null, "to": "pending_acceptance", "actor": "customer", "at": "…" },
    { "from": "pending_acceptance", "to": "accepted", "actor": "staff", "at": "…" }
  ]
}
```

- `name` من `item_name_snapshot`، و`unitPrice` من `unit_price_snapshot`. **لا ربط مع `menu_items`.** الطلب القديم يبقى باسمه وسعره لحظة الطلب — **والزبون دفع القديم**.
- `lineTotal` محسوب في SQL.
- الاستلام: `deliveryFee = "0.00"` و`deliveryAddress = null`.
- `history` بالترتيب الزمني.
- `id` ليس UUID صالحا ← 400. غير موجود أو لمطعم آخر ← 404.

### 3.3 · `PATCH /orders/:id/status`

**الطلب:** `{ "from": "…", "to": "…", "cancellationReason"?: "…" }` · **الرد 200:** الطلب بشكل عنصر §3.1.

**بترتيب الفحص:**

| # | الشرط | الرد |
|---|---|---|
| 1 | مدخل غلط: وجهة `expired` أو `pending_acceptance`، أو سبب مع وجهة غير الإلغاء | 400 |
| 2 | `from → to` ليس في §2.6 | 409 `transition_not_allowed` |
| 3 | CAS أعاد 0 صفوف، والطلب غير موجود تحت سياق المطعم | 404 |
| 4 | CAS أعاد 0 صفوف، والطلب موجود | 409 `status_conflict` ومعه `currentStatus` |

**ترانزاكشن واحدة عبر `TenantDbService`:**

1. `UPDATE orders SET status = $to, notified = false …` **`WHERE id = $id AND status = $from`**، ومعه `RETURNING` لحقول الرد.
   - وجهة `completed`: `payment_status = 'collected'` **في نفس الـUPDATE**.
   - وجهة `cancelled`: `cancelled_by = 'staff'` و`cancellation_reason`.
2. **إن أعاد صفرا:** `SELECT status FROM orders WHERE id = $id` **داخل نفس الترانزاكشن**. لا صف ← 404. صف ← 409 ومعه `currentStatus`. **هذا هو ما يفرّق بين 404 و409**، وهو السبب الوحيد لقراءة الحالة هنا — لا لبناء الـUPDATE عليها (§2.7).
3. `INSERT order_status_history`: `from_status = $from` · `to_status = $to` · `actor = 'staff'` · `actor_staff_id` **من التوكن**.
4. **الرد 200** بنفس إسقاط §3.1 لطلب واحد (ومنه `itemCount`)، بنفس الاستعلام لا بإسقاط ثانٍ.
5. أي فشل = رجوع الترانزاكشن كلها. **لا طلب تغيّرت حالته بلا سطر تاريخ.**

🔴 **القيود في القاعدة شبكة أمانك:** `actor='staff'` ⟺ `actor_staff_id IS NOT NULL` · مكتمل ⇒ محصَّل. **لا تلتفّ عليها.**

### 3.4 · `GET /menu-items` و`PATCH /menu-items/:id`

- `GET`: `{ "items": [{ "id", "name", "price": "2.50", "isAvailable": true }] }` **بترتيب المنيو الذي يراه الزبون**، بلا المؤرشف.
- `PATCH`: `{ "isAvailable"?: boolean, "price"?: "3.00" }`، **حقل واحد على الأقل**. الرد: الصنف بعد التعديل.
- `price` بالنمط `^(?!0+(?:\.0+)?$)\d{1,6}(?:\.\d{1,2})?$` — **الصفر مرفوض بالنمط نفسه، لا بتحويل رقمي في JS**.
- 🔴 **`isAvailable` يكتب العمود نفسه الذي يقرؤه فحص «أكّد» في المحرّك (الفحص 6)، لا عمودا شبيها.**
- **«السعر وعد»:** تعديل السعر لا يمسّ سلّة قائمة ولا طلبا قائما. الـsnapshot يحميهما.

### 3.5 · `GET /restaurant/settings` و`PATCH /restaurant/settings`

- **بلا `:id` في المسار أصلا.** المطعم من التوكن.
- `GET`: `{ "currency", "offersDelivery", "deliveryFee": "1.50", "contactPhone", "openingHours" }`.
- `PATCH` جزئي: `deliveryFee` · `contactPhone` · `openingHours`. إرسال `currency` أو `offersDelivery` ← 400.
- `deliveryFee` بالنمط `^\d{1,6}(?:\.\d{1,2})?$` (الصفر مقبول).
- `contactPhone` بالنمط `^\+[1-9]\d{7,14}$`.
- `openingHours`: **الأسبوع كاملا يُستبدَل دفعة واحدة، بالشكل الذي يقرؤه المحرّك حرفيا** (الفحص 7). إن كانت جدولا منفصلا: حذف أسطر المطعم وإدراجها في نفس الترانزاكشن.
- **«الرسوم وعد»:** تعديلها لا يمسّ جلسة اختارت «توصيل» (`12-after-cart-brief.md` §2.4).

### د-4 · تغيير الحالة

**الإنجاز:**
- المسار الكامل `pending_acceptance ← accepted ← preparing ← ready ← completed`، سطر تاريخ لكل خطوة، و`actor_staff_id` من التوكن
- `preparing ← completed` مباشرة
- 🔴 **طلبان بنفس اللحظة على نفس الطلب ونفس `from`:** واحد 200، والآخر 409، **وسطر تاريخ واحد**
- 🔴 **شاشة قديمة:** `from = pending_acceptance` و`to = cancelled`، والطلب صار `preparing` ← 409 ومعه `currentStatus`، **والطلب لم يُلغَ**
- كل انتقال ممنوع له اختبار باسمه: من نهائية · تخطٍّ · رجوع
- `completed` ← `collected` تلقائيا
- كل انتقال ناجح ← `notified = false`
- الإلغاء: `cancelled_by = 'staff'`، والسبب محفوظ كما كُتب بعد القصّ، والفارغ NULL
- موظف ب على طلب أ ← 404
- 🔴 **فشل مفروض عند إدراج سطر التاريخ — بعد الـUPDATE لا قبله** ← الحالة لم تتغيّر. اختبار يفشل بخطوة مبكرة لا يحرس رجوع خطوة متأخرة (درس ج-5). الطريقة: استبدل كاتب التاريخ في وحدة الاختبار بواحد يرمي بعد الـUPDATE، أو trigger اختباري يرفض الإدراج لطلب بعينه
- `dashboard-api` لا يستورد مرسِل واتساب (الفحص 13). إن كان مستوردا لأي سبب: **صفر نداءات** في كل اختبارات د-4، بمرسِل وهمي يسجّل النداءات
- `verify` = 0

**ضوابط الكسر:**

| الكسر | المتوقع أن يسقط | لماذا |
|---|---|---|
| احذف `AND status = $from` | «طلبان بنفس اللحظة» و«شاشة قديمة» | الاثنان ينجحان بسطرَي تاريخ، وطلب يُلغى من المطبخ |
| احذف `AND status = $from` **وأضف `SELECT … FOR UPDATE` قبله** | **اكتب قبل التشغيل:** أي الاختبارين يسقط في بنية كودك تحديدا، ولماذا؟ | إن تنبأت خطأ، فأنت لا تعرف أي آلية تحميك (درس ج-5) |
| احذف `payment_status = 'collected'` | «`completed` ← `collected`»، **بخطأ قيد من القاعدة** | القيد هو الشبكة. إن مرّ بصمت، فالقيد غير موجود — **قف** |
| أرجع 200 عند `rowcount = 0` | «طلبان بنفس اللحظة» | الموظف يظن أن ضغطته نفذت |
| أدرج سطر التاريخ في ترانزاكشن منفصلة | «فشل مفروض عند التاريخ» | حالة تغيّرت بلا تاريخ |

### د-5 · المنيو: التوفّر والسعر

**الإنجاز:**
- `GET` بترتيب المنيو، بلا المؤرشف، والسعر نص
- 🔴 **`PATCH isAvailable = false` ← العمود الذي يقرؤه فحص «أكّد» (الفحص 6) صار false.** التأكيد باسم العمود مباشرة في القاعدة، **لا عبر قراءة الـAPI نفسه**. ومع اختبار المحرّك القائم (صنف غير متوفر بين الملخّص و«أكّد»)، يثبت هذا أن اللوحة والمحرّك يتكلمان عن نفس العمود. إن لم يكن ذلك الاختبار موجودا، اذكره في التقرير
- تعديل السعر ← الطلب القائم بسعره القديم عبر `GET /orders/:id`
- `price` صفر أو سالب أو بثلاث خانات عشرية أو ليس نصا ← 400 · **`٢.٥٠` بأرقام عربية-هندية ← 400** · جسم فارغ ← 400
- صنف مطعم أ من موظف ب ← 404
- `verify` = 0

**ضابط الكسر:** اجعل الـAPI يكتب عمودا شبيها غير الذي يقرؤه المحرّك ← يسقط اختبار العمود: **الموظف يطفئ الصنف والزبون يطلبه عادي.** هذا أخطر خطأ صامت في د-5.

### د-6 · إعدادات المطعم

**الإنجاز:**
- `GET` يرجع الحقول الخمسة، والمال نص
- `PATCH` لكل حقل وحده، ولها مجتمعة
- `currency` أو `offersDelivery` في الطلب ← 400 · `deliveryFee` بأرقام عربية-هندية ← 400
- 🔴 **ذهاب وإياب للساعات:** `PATCH` لجدول أسبوعي، ثم دالة «مفتوح أم مغلق» التي يستعملها المحرّك تعطي الجواب المتوقع في ساعة داخل الدوام وأخرى خارجه. إن كانت الدالة في المحرّك وبوابة العزل تمنع استيرادها من هنا: قارن المخزَّن حرفيا بالشكل الذي تستعمله اختبارات المحرّك القائمة، **واكتب ذلك في التقرير**

- `verify` = 0

## 5. أخطاء صامتة — راجعها قبل الدمج

1. **`restaurant_id` من الطلب** ← مطعم يرى طلبات مطعم. الاختبارات تمرّ إن استعملت نفس المعرّف في التوكن والطلب.
2. **المال إلى `number`** ← `"13.50"` تصير `13.5`، والشاشة تعرض غير الفاتورة.
3. **اقرأ ثم اكتب بلا CAS** ← آخر موظف يمحو شغل الأول.
4. **التاريخ خارج الترانزاكشن** ← حالة بلا سجل.
5. **403 بدل 404** ← يكشف للمطعم الآخر أن الطلب موجود.
6. **عمود توفّر غير الذي يقرؤه المحرّك** ← الموظف يطفئ الصنف والزبون يطلبه.
7. **شكل ساعات لا يفهمه المحرّك** ← المطعم **مفتوح في نظر المحرّك وهو مغلق**: يقرأ الأسبوع الذي لا يعرف فيه يوما «مفتوحا دائما» (§8.8). *(صُحّح في د-7، 23 سبتمبر: كان «مغلق في نظر المحرّك»)*
8. **`MAX() + 1` بلا قفل** ← في الذروة يفشل إنشاء طلب. لا يظهر إلا بتزامن حقيقي.
9. **`await` ناقصة** ← `Promise` بدل قيمة، والمنطق يكمل بقيمة غلط.

🔴 **لا يُسقط أيٌّ منها الاختبارات إلا إذا كان له اختبار مقصود. اكتبه.**

### 8.1 · مصدر المطعم: الحارس القائم، لا التوكن

**الواقع صحيح والبريف أخطأ.** التوكن لا يحمل `restaurant_id` عمدا (`auth.types.ts:2`)، لأن الموظف قد يكون عضوا في أكثر من فرع. و`RestaurantContextGuard` يتحقّق من العضوية عبر `app.verify_membership` قبل ضبط سياق RLS. **الخطر الذي أراد §0 منعه هو معرّف من الطلب بلا تحقّق، والحارس القائم يمنعه.**

**القاعدة السارية بدل «المطعم» في §0:**

- 🔴 **`restaurant_id` هو ما تحقّق منه `RestaurantContextGuard`، لا غير.** كل مسار في د عليه `@UseGuards(RestaurantContextGuard)`، والمعرّف يُقرأ من السياق الذي ضبطه الحارس. **ممنوع قراءته من الهيدر أو body أو query أو params مباشرة في أي كود خارج الحارس.**
- كل استعلام عبر `TenantDbService`، كما في §0.
- **لا تعدّل الحارس ولا المصادقة.**
- 🔴 **لا يُسمّى أي باراميتر مسار في د `restaurantId`.** الحارس يقرأ `req.params.restaurantId` قبل الهيدر، فباراميتر بهذا الاسم يغيّر مصدر المطعم بصمت.
- سلوك الحارس مع هيدر لمطعم ليس الموظف عضوا فيه **يبقى كما هو**. قاعدة 404 في §2.9 تخصّ **معرّف مورد** لمطعم آخر داخل سياق صالح.

**§5 رقم 1 يُقرأ:** «قراءة المعرّف من الهيدر مباشرة بدل سياق الحارس ← مطعم يرى طلبات مطعم».

**اختبارات العزل في د-2 تصير ثلاثة:**
- موظف ب وحده، بهيدر ب: طلب أ لا يظهر.
- موظف ب وحده، بهيدر أ: يرفضه الحارس بالرمز الذي تفحصه اختباراته اليوم، وصفر طلبات.
- 🔴 **موظف الفرعين (من الـseed):** بهيدر أ يرى طلب أ وحده، وبهيدر ب يرى طلب ب وحده. **هذا أهم اختبار في د**، لأنه الحالة التي لا يغطيها «التوكن لا يحمل المطعم» بنفسه.

**ضابطا الكسر في د-2 يحلّان محل الأول:**

| الكسر | المتوقع أن يسقط | لماذا |
|---|---|---|
| انزع `@UseGuards(RestaurantContextGuard)` عن مسار القائمة واضبط السياق من الهيدر الخام | «موظف ب بهيدر أ» | هيدر بلا تحقّق عضوية = أي موظف يقرأ أي مطعم |
| أبقِ الحارس، واحذف أي فلتر `restaurant_id` صريح من استعلام القائمة (إن وُجد) | **اكتب قبل التشغيل:** هل يسقط شيء؟ | المتوقع لا، لأن RLS هي الحماية الفعلية. **إن سقط اختبار، فـRLS لا تعمل كما نظن: قف** |

### 8.2 · `cancelled_by = 'restaurant'`

- الـenum القائم: `('customer', 'restaurant', 'system')`. الإلغاء من اللوحة يكتب **`'restaurant'`**، ويطابق مفتاح `ORDER_STATUS_MESSAGE_AR.cancelled`.
- أينما ورد `'staff'` لـ`cancelled_by` في §2.8 و§3.3 ود-4، يُقرأ `'restaurant'`.
- **`actor = 'staff'` في `order_status_history` باقٍ كما هو** — enum آخر.

### 8.3 · لا أرشفة. التصنيف المطفأ هو المعيار

- «بلا المؤرشف» في §3.4 ود-5 **تُحذف**. لا مفهوم أرشفة في `menu_items`.
- `GET /menu-items` يرجع أصناف المطعم **ومنها غير المتوفر**، لأن الموظف يحتاجه ليعيد تشغيله.
- **ويستثني أصناف التصنيفات المطفأة** (`menu_categories.is_active = false`). السبب: المحرّك يعدّها غير متوفرة مهما كان `is_available`. لو ظهرت، الموظف يشغّل الصنف والزبون لا يستطيع طلبه — **بلا أي خطأ**. تشغيل التصنيف خارج د.
- الترتيب: **ترتيب الزبون حرفيا** — `category.display_order, name, id` ثم `item.display_order, name, id`.
- `PATCH` لا يتغيّر.
- إنجاز إضافي في د-5: صنف في تصنيف مطفأ لا يظهر في `GET`.

### 8.4 · العملة خانة في القوالب، لا منسّق

- **`formatMinor` لا يُمسّ**: يرجع الرقم وحده، كما اليوم.

### 8.5 · تعديل التصديرات النصية القائمة مسموح في د-1 — بحدود

- §0 «تصدير جديد، لا تعديل لتصدير قائم» **يخصّ أنواع ردود الـAPI وحدها.**

- اختباراتها تتغيّر لأن قرارها تغيّر (`12-after-cart-brief.md` §15.5). **ولا تصدير نصي غيرها يُلمس.**

### 8.6 · الأسئلة الصغيرة

| | القرار |
|---|---|
| **`ready_at`** | يُضبط `now()` عند الدخول إلى `ready`، في نفس الـUPDATE. بدونه مهلة الـ24 ساعة (Sprint 2) لن تعمل على طلبات البايلوت. `preparing ← completed` مباشرة يتركه NULL |
| **`updated_at`** | `updated_at = now()` في كل UPDATE في د (`orders` · `menu_items` · `restaurants`) حيث العمود موجود. لا trigger يضبطه |
| **`order_status_history.reason`** | عند الإلغاء: نفس السبب المقصوص في `orders.cancellation_reason` وفي `reason`، في نفس الترانزاكشن. NULL في غير الإلغاء |
| **طلب غير نقدي** | وجهة `completed`: `payment_status = 'collected'` **لطلب `cash` فقط**. ويُضاف إلى الـWHERE: `AND (payment_method = 'cash' OR payment_status = 'paid')`. اختبار باسمه على طلب المطعم ب (`online`) من الـseed ← 409 `payment_not_settled` |
| **جدول الانتقالات** | تصدير جديد في `shared`: `STAFF_TRANSITIONS` بجدول §2.6 حرفيا، **واختبار أنه جزء من `ALLOWED_TRANSITIONS`**. `canTransition` وحدها لا تكفي، لأن فيها `ready ← expired` |

**تمييز 404 من 409 في §3.3 خطوة 2** يصير: `SELECT status, payment_method, payment_status` داخل نفس الترانزاكشن. لا صف ← 404 · `status ≠ from` ← 409 `status_conflict` · غير ذلك ← 409 `payment_not_settled`.

### 8.7 · صيغة الأخطاء

- **400:** صيغة `nestjs-zod` الافتراضية القائمة. لا تُغيَّر.
- **404:** صيغة Nest الافتراضية.
- **409:** شكل Nest الافتراضي، ومعه `code`:

  ```json
  { "statusCode": 409, "error": "Conflict", "code": "status_conflict", "message": "…", "currentStatus": "preparing" }
  ```

- `code` واحد من ثلاثة: `transition_not_allowed` · `status_conflict` · `payment_not_settled`. و`currentStatus` مع `status_conflict` وحدها.
- **الشاشة تقرأ `code` لا `message`.** `message` إنجليزي للمطوّر، والنص العربي للموظف مكانه بريف الشاشة.
- نوع جسم الـ409 في `shared`، تصديرا جديدا.
- **اختبارات د-4 تفحص الجسم، لا رمز الحالة وحده.**

### 8.8 · ساعات الدوام: الكاتب صارم، والقارئ متسامح

- ضابط الكسر في د-6 كما كُتب **لا يُسقط شيئا**: المحرّك يقبل `"9:00"` (`TIME_RE`) و`"sunday"` (`normaliseDayKey`).
- **القاعدة:** مخطط Zod لـ`openingHours` يقبل **الشكل القانوني وحده**: `{ days: { sun: [{ open: "HH:MM", close: "HH:MM" }] } }` — مفاتيح الأيام بالشكل المخزَّن في الـseed، والساعات بخانتين دائما. **ما يقبله المحرّك تسامحا لا يُكتب من اللوحة.**
- `decideHours` لا تُستورد (بوابة الاعتمادات). البديل المقبول في د-6 سارٍ: مقارنة حرفية بالشكل الذي تستعمله اختبارات المحرّك.
- **الضابط الساري:** اجعل الكاتب يكتب مفاتيح أيام رقمية، أو `{from, to}` بدل `{open, close}` ← يسقط «ذهاب وإياب».
- إنجاز إضافي: `"9:00"` و`"sunday"` في `PATCH` ← 400.
- `timezone` لا يُعدَّل من اللوحة.

### 8.9 · ملاحظات لبريف الشاشة — لا تُنفَّذ في د

- `customers.name` فارغ عمليا لكل زبون حقيقي، لأن المحرّك لا يكتبه (`session.service.ts:371`). **الشاشة تعرض الهاتف.**
- طلب المطعم ج في الـseed بلا أصناف، و`itemCount = 0` مقبول.
- هيدر `x-restaurant-id` إلزامي في كل نداء من الشاشة، وموظف الفرعين يحتاج مبدّل فرع.

### 8.10 · ما لم يتغيّر

د-1 بمواصفتها في §2.1 إلى §2.4 سارية، مع §8.4 و§8.5. والعقود في §3 سارية مع §8.1 و§8.2 و§8.3 و§8.6 و§8.7. **وترتيب المهام في §4 كما هو.**

### 9.3 · `PATCH /orders/:id/status`

**الطلب** (`UpdateOrderStatusRequest`) — كائن صارم، **أي مفتاح زائد ← 400** (ومنه `restaurantId`):

```json
{ "from": "pending_acceptance", "to": "cancelled", "cancellationReason": "نفد الخبز" }
```

| الحقل | القاعدة |
|---|---|
| `from` | إلزامي. أي حالة من السبع. **الحالة التي يعرضها الموظف على شاشته**، لا ما تظنه الشاشة الآن (§2.7) |
| `to` | إلزامي. `accepted` · `preparing` · `ready` · `completed` · `cancelled` (`STAFF_TARGET_STATUSES`). `pending_acceptance` و`expired` ← 400 |
| `cancellationReason` | اختياري، ومع `to: "cancelled"` وحدها — وجوده مع غيرها ← 400 **حتى لو فارغا**. يُقصّ من الطرفين، والحدّ 300 حرف **بعد القصّ**، والفارغ بعد القصّ يُخزَّن NULL |

**الانتقالات** — `STAFF_TRANSITIONS` في `shared`، وهي جدول §2.6 حرفيا:

| من | إلى |
|---|---|
| `pending_acceptance` | `accepted` · `cancelled` |
| `accepted` | `preparing` · `cancelled` |
| `preparing` | `ready` · `completed` · `cancelled` |
| `ready` | `completed` · `cancelled` |
| `completed` · `cancelled` · `expired` | لا شيء |

🔴 **بوابة الدفع** (د-4 ود-4.1): الوجهتان `accepted` و`completed` تشترطان `payment_method = 'cash'` **أو** `payment_status = 'paid'`. الإلغاء مفتوح دائما.

**بترتيب الفحص:**

| # | الشرط | الرد |
|---|---|---|
| 1 | الجسم أو `:id` فاسد | 400 تحقّق |
| 2 | `from → to` ليس في `STAFF_TRANSITIONS` — قبل أي استعلام | 409 `transition_not_allowed` |
| 3 | الـCAS أعاد صفرا، ولا طلب بهذا المعرّف تحت سياق المطعم | 404 |
| 4 | الـCAS أعاد صفرا، والحالة الحقيقية ليست `from` | 409 `status_conflict` ومعه `currentStatus` |
| 5 | الـCAS أعاد صفرا، والحالة `from`، فالسبب بوابة الدفع | 409 `payment_not_settled` |
| 6 | نجح | 200 |

**جسم الـ409** (`OrderStatusConflictBody`) — `message` إنجليزي للمطوّر، **والشاشة تقرأ `code` وحده**:

```json
{ "statusCode": 409, "error": "Conflict", "code": "status_conflict", "message": "the order is preparing, not pending_acceptance", "currentStatus": "preparing" }
{ "statusCode": 409, "error": "Conflict", "code": "transition_not_allowed", "message": "ready → accepted is not a staff transition" }
{ "statusCode": 409, "error": "Conflict", "code": "payment_not_settled", "message": "only a cash order, or a paid one, can be accepted" }
```

`currentStatus` مع `status_conflict` وحدها.

**الرد 200** (`UpdateOrderStatusResponse` = `OrderListItem`): الطلب بعد التغيير، **بنفس شكل عنصر §9.1 وبنفس الإسقاط**.

**ما يُكتب، في ترانزاكشن واحدة:**
- `UPDATE orders … WHERE id = :id AND status = from` (+ بوابة الدفع): `status` · `notified = false` · `updated_at = now()`، ومعها حسب الوجهة:
  - `ready`: `ready_at = now()`.
  - `completed`: `payment_status = 'collected'` **للنقدي وحده**؛ الأونلاين يصل `paid` ويبقى `paid`.
  - `cancelled`: `cancelled_by = 'restaurant'` و`cancellation_reason`.
- `INSERT order_status_history`: `from_status = from` · `to_status = to` · `actor = 'staff'` · `actor_staff_id` من التوكن · `reason` = السبب المقصوص عند الإلغاء، وNULL في غيره.
- أي فشل ← رجوع الاثنين معا.

**الأخطاء:** 400 · 401 · 403 · 404 · 409.

### 9.4 · `GET /menu-items`

**الرد 200** (`MenuItemListResponse`):

```json
{ "items": [ { "id": "…uuid…", "name": "منسف", "price": "8.00", "isAvailable": true } ] }
```

- **كل أصناف المطعم، ومنها غير المتوفرة** — الموظف يحتاجها ليعيد تشغيلها.
- **بلا أصناف التصنيفات المطفأة** (`menu_categories.is_active = false`).
- **ترتيب الزبون حرفيا:** `category.display_order, name, id` ثم `item.display_order, name, id` — نسخة من `ORDER BY` في `readMenu` بالمحرّك (فجوة §10).
- بلا صفحات. **الأخطاء:** 401 · 403.

### 9.5 · `PATCH /menu-items/:id`

**الطلب** (`UpdateMenuItemRequest`) — كائن صارم، **حقل واحد على الأقل** (`{}` ← 400)، وأي مفتاح آخر (`name`، `restaurantId`) ← 400:

| الحقل | القاعدة |
|---|---|
| `isAvailable` | `boolean`. يكتب `menu_items.is_available` — **العمود نفسه الذي يقرؤه فحص «أكّد» في المحرّك** |
| `price` | **نص**، بالنمط `MENU_PRICE_PATTERN` = `^(?!0+(?:\.0+)?$)\d{1,6}(?:\.\d{1,2})?$`. الصفر بكل أشكاله ← 400 · سالب · ثلاث خانات عشرية · `number` بدل نص · `٢.٥٠` ← 400. يُكتب `::numeric(12,2)` في SQL |

- `:id` بـ`z.guid()` ← 400 إن فسد.
- **الرد 200** (`UpdateMenuItemResponse` = `MenuItemListItem`): الصنف بعد التعديل. **يُكتب ما أُرسل وحده**، و`updated_at = now()`.
- صنف في تصنيف مطفأ: **200، ويُكتب** — مع أنه لا يظهر في `GET` (§10).
- تعديل السعر لا يمسّ سلّة ولا طلبا قائما («السعر وعد»).
- **الأخطاء:** 400 · 401 · 403 · 404 (غير موجود أو لمطعم آخر، نفس الجسم).

### 9.6 · `GET /restaurant/settings`

**بلا `:id`.** المطعم من الهيدر.

**الرد 200** (`RestaurantSettings`):

```json
{
  "currency": "JOD",
  "offersDelivery": true,
  "deliveryFee": "1.50",
  "contactPhone": "0790000099",
  "openingHours": { "days": { "sun": [{ "open": "09:00", "close": "23:00" }], "mon": [], "…": [] } }
}
```

- `currency` و`offersDelivery` **للقراءة فقط**.
- `contactPhone` قد يكون `null`.
- 🔴 **`openingHours` يُرجَع كما هو مخزَّن، بلا أي تحويل.** لمطعم جديد: **`{}`** (افتراضي العمود، ومعناه في المحرّك «مفتوح دائما»). وصف كُتب يدويا قبل الشاشة قد يحمل شكلا يقبله المحرّك تسامحا ولا يقبله الـPATCH (`"sunday"`، `"9:00"`).
- **الأخطاء:** 401 · 403 · 404 (لا يُصل إليه عمليا: الحارس يتحقّق من المطعم قبله).

### 9.7 · `PATCH /restaurant/settings`

**الطلب** (`UpdateRestaurantSettingsRequest`) — كائن صارم على كل مستوى، **حقل واحد على الأقل**. `currency` أو `offersDelivery` أو `timezone` أو أي مفتاح آخر ← 400:

| الحقل | القاعدة |
|---|---|
| `deliveryFee` | نص بالنمط `DELIVERY_FEE_PATTERN` = `^\d{1,6}(?:\.\d{1,2})?$`. **الصفر مقبول** (توصيل مجاني). أرقام عربية-هندية ← 400. يُكتب `::numeric(12,2)` |
| `contactPhone` | نص بالنمط `CONTACT_PHONE_PATTERN` = `^\+?[0-9]{7,15}$`: محلي (`0790000099`) أو دولي (`+962790000099`)، بلا مسافات ولا شرطات. **`null` يمسحه** |
| `openingHours` | الأسبوع كاملا، يُستبدَل دفعة واحدة. الشكل أدناه حرفيا |

**`openingHours` — الشكل القانوني وحده:**

```json
{ "days": {
    "sun": [{ "open": "09:00", "close": "23:00" }],
    "mon": [], "tue": [], "wed": [], "thu": [],
    "fri": [{ "open": "13:00", "close": "02:00" }],
    "sat": [{ "open": "09:00", "close": "15:00" }, { "open": "18:00", "close": "23:00" }] } }
```

- 🔴 **المفاتيح السبعة إلزامية في كل PATCH:** `sun` · `mon` · `tue` · `wed` · `thu` · `fri` · `sat` (`OPENING_DAYS`). اليوم المغلق `[]`، **لا مفتاح غائب**. `{}` و`{ "days": {} }` ← 400.
- كل وقت `HH:MM` بخانتين، `00:00` إلى `23:59`: `"9:00"` و`"24:00"` ← 400.
- النافذة كائن `{open, close}` صارم: `{from, to}` ← 400.
- نافذة `close` فيها قبل `open` **تعبر منتصف الليل** (`13:00` ← `02:00`).
- **مطعم 24 ساعة يُكتب بنافذتين: `00:00–12:00` و`12:00–00:00`.** نافذة `00:00–00:00` يحذفها المحرّك (صفرية)، فلا تُستعمل.
- `timezone` عمود منفصل، لا يُكتب من هنا.

**الرد 200** (`UpdateRestaurantSettingsResponse` = `RestaurantSettings`): الإعدادات بعد التعديل. **يُكتب ما أُرسل وحده**، و`updated_at = now()`. تعديل الرسوم لا يمسّ جلسة اختارت «توصيل» ولا طلبا («الرسوم وعد»).

**الأخطاء:** 400 · 401 · 403 · 404 (لا يُصل إليه عمليا).

### 9.8 · مسارات قائمة قبل د — للشاشة، لم تتغيّر في د

| المسار | الحماية | الطلب | الرد 200 |
