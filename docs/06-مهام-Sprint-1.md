## المسار A — محرك المحادثة (BE1)

### S1-01 — نقطة webhook واتساب: التحقق والتوقيع
**BE1 · ٦ ساعات · بلا اعتماديات · مخطط ٦.٣**

```
GET  /webhooks/whatsapp   ← ميتا بتتحقق من الرابط مرة وحدة
POST /webhooks/whatsapp   ← كل رسالة واردة
```

**GET:** ميتا بتبعت `hub.mode` و `hub.verify_token` و `hub.challenge`. لو الـtoken بيطابق `WHATSAPP_WEBHOOK_VERIFY_TOKEN`، رجّع **الـchallenge كنص خام** بحالة 200. أي شي تاني → 403.

**POST:** 🔴 **تحقق من توقيع `X-Hub-Signature-256` قبل أي شي.** HMAC-SHA256 على **جسم الطلب الخام** (raw body) بمفتاح `WHATSAPP_APP_SECRET`.

> ⚠️ **مصيدة NestJS:** الـbody parser الافتراضي بيحوّل الطلب لـJSON، والتوقيع بينحسب على **البايتات الخام**. لازم تفعّل `rawBody` على هالمسار تحديدا. لو حسبته على JSON معاد التسلسل، **التوقيع بيفشل دايما** وبتصرف نص يوم تدوّر على السبب.
>
> **وبدون التحقق:** أي حدا بيعرف رابطك بيقدر يبعت طلبات مزوّرة ويعمل طلبات وهمية باسم زبائن مش موجودين.

**القبول:** GET بيرجّع الـchallenge · توقيع غلط → **401 والطلب ينرمى قبل أي منطق** · توقيع صح → 200 · حالة الفشل مسجّلة بـPino

### S1-03 — بوابة منع التكرار
**BE1 · ٤ ساعات · بيعتمد على S1-02 · مخطط ٦.٣**

استخدم `claimWebhookEvent()` من `critical-primitives.ts`. **ما تعيد كتابتها.**

هي أول شي بعد التحقق من التوقيع، **قبل أي منطق جلسة أو طلب.**

```ts
if (!(await claimWebhookEvent(tx, message.id, 'whatsapp'))) return ok(); // مكرر، انتهى
```

🔴 **ليش `INSERT ... ON CONFLICT DO NOTHING RETURNING` مش `SELECT` بعدين `INSERT`:** لأنها **عملية ذرية واحدة**. مع SELECT-ثم-INSERT، إعادة إرسال بتصل بفارق ميلي ثانية بتمر الاثنين من الـSELECT قبل ما ينكتب أي صف → **طلبين**.

**القبول:** نفس `message_id` مرتين → الثانية بترجّع 200 و **ما بتعمل ولا صف** · نفس المعرّف من مصدر مختلف بينعالج مستقل · صف بينكتب بـ`processed_webhook_events`

### S1-04 — تحديد المطعم والزبون والجلسة
**BE1 · ٨ ساعات · بيعتمد على S1-03 و S0-09 · مخطط ٦.٣**

```
phone_number_id (من الحمولة)
  → app.resolve_restaurant_by_phone_id()    ← SECURITY DEFINER، التجاوز الوحيد
  → set_config('app.current_restaurant_id') ← من هون كل شي تحت RLS
  → upsert الزبون على (restaurant_id, phone_number)
  → جلسة نشطة؟ استكمل : أنشئ جديدة
```

🔴 **بعد `resolve_restaurant_by_phone_id` مباشرة، اضبط السياق.** المحرك ما عنده موظف مسجّل دخول، فما فيه Guard — التجاوز الوحيد هو الدالة الضيقة هاي، وكل شي بعدها محمي بـRLS زي الداشبورد بالضبط.

الجلسة النشطة = `state NOT IN ('order_placed','abandoned')`، الأحدث حسب `last_message_at`.

**القبول:** `phone_id` مجهول → 200 + log (**مش استثناء**) · زبون جديد → صف بـ`customers` وجلسة `state='new'` · زبون موجود بجلسة نشطة → **بيستكمل، ما بيعيد من الصفر** · زبون بجلسة `order_placed` → جلسة جديدة · 🔴 **اختبار: زبونين بنفس الرقم عند مطعمين مختلفين = صفّين منفصلين تماما**

### 🔴 S1-13 — إنشاء طلب الكاش
**BE1 · ٨ ساعات · بيعتمد على S1-12 · FR-10 (نصف الكاش) · مخطط ٦.١**

**قلب الـSprint كله.** كل شي قبله كان تمهيد لهالمهمة.

```
BEGIN
  advanceSessionState(session, 'fulfillment_choice' → 'order_placed')   ← CAS
  rowcount = 0 ? ROLLBACK (ضغطة مكررة، انتهى)
  INSERT orders   (payment_method='cash', status='pending_acceptance',
                   payment_status='pending_cash', notified=false, created_at=now())
  INSERT order_items  (بلقطات الاسم والسعر)
  INSERT order_status_history (NULL → 'pending_acceptance', actor='customer')
COMMIT
→ رسالة تأكيد للزبون
```

🔴 **كله جوا transaction واحدة** (NFR-04: "فشل بالنص ما بيخلّي حالة جزئية").

🔴 **الـCAS مش اختيارية.** الزبون بيضغط "تأكيد" مرتين بسرعة → **رسالتين مختلفتين بمعرّفين مختلفين** → بوابة منع التكرار بتمررهم الاثنين (وهذا صحيح!). الوحيد اللي بيمسكها هو `UPDATE ... WHERE state = 'fulfillment_choice'` — بتنجح مرة وحدة بالضبط.

**لقطات الأسعار (`item_name_snapshot`, `unit_price_snapshot`) إلزامية.** لو المطعم غيّر السعر بكرا، الطلب القديم لازم يضل يعرض السعر اللي دفعه الزبون.

**القبول:**
- طلب كامل بينشأ بـtransaction وحدة
- 🔴 **ضغطتين متتاليتين → طلب واحد بالضبط** (اختبار آلي)
- فشل بإدخال الأصناف → **rollback كامل، ولا صف طلب يتيم**
- `order_status_history` فيها صف الإنشاء
- الطلب بيظهر بلوحة المطعم خلال ٥ ثواني
- الزبون بيوصله تأكيد

```
4. 🔴 بوابة القبول: أونلاين + مش مدفوع     → 400 "لا يمكن قبول الطلب قبل تأكيد الدفع"
5. canTransition(from, to) من @sufria/shared  → 400
6. BEGIN → UPDATE + INSERT history → COMMIT
```

🔴 **الخطوة ٤ بتنكتب من هلق حتى لو الدفع الإلكتروني مش مبني.** أسهل بكتير من إضافتها بـSprint 2 على كود شغّال، وأسلم — نسيانها بيخلي المطعم يحضّر طلب ما انحسبت فلوسه.

🔴 **الخطوة ٥ بتستورد من `@sufria/shared`، ما بتتكرر هون.** نفس السطر اللي الواجهة بتعطّل فيه الأزرار.

⚠️ `completed` بتنقل `payment_status` من `pending_cash` لـ`collected` **بنفس الـtransaction** (NFR-09). القيد `orders_completed_payment_settled` بالقاعدة بيرفض غير هيك — **لو نسيتها، الـINSERT بيفشل وبتعرف فورا.**

**القبول:** الانتقالات المسموحة بتشتغل · الممنوعة → 400 · طلب أونلاين غير مدفوع → **400 بالرسالة العربية بالضبط** · `completed` على كاش → `payment_status='collected'` · كل انتقال بيسجّل بالـhistory مع معرّف الموظف · موظف مطعم تاني → 403

### S1-16 — درج تفاصيل الطلب + أزرار الحالة
**FE · ١٠ ساعات · بيعتمد على S1-08 و S1-15 · برومبتات شاشة ٣ و ٤**

درج بينفتح من اليمين: رقم الطلب والحالة · الزبون · طريقة الاستلام والدفع · الأصناف بالتفصيل · المجاميع · **الخط الزمني** · الأزرار.

🔴 **بوابة القبول بالواجهة:**
```tsx
const enabled = canAcceptOrder(order);   // من @sufria/shared — نفس دالة الباك اند
```
لما تكون معطّلة: **دايما تحتها سطر شرح** — `لا يمكن قبول الطلب قبل تأكيد الدفع`.

> `DESIGN.md` §7: **زر معطّل بلا سبب مكتوب ممنوع.** موظف بيشوف زر ميّت بلا تفسير بيفترض إن النظام خربان، وبيتصل عليك.

- نافذة تأكيد الإلغاء: عنوان + تحذير + حقل سبب اختياري + زرين (تأكيد بلون مدمّر / تراجع)
- شريط انقطاع الاتصال لما الـpolling يفشل

**القبول:** الدرج بيفتح من اليمين · الخط الزمني بيبيّن مين ومتى · **الأزرار المسموحة بس ظاهرة نشطة** (من `canTransition`) · الزر المعطّل معه سبب دايما · الإلغاء بيطلب تأكيد · انقطاع الشبكة → شريط عنبري مش صفحة بيضا

### S1-17 — 🎯 بروفة العرض من طرف لطرف
**الكل · ٤ ساعات · الخميس ٣ سبتمبر · بيعتمد على كل شي فوق**

**نفّذوا السيناريو كامل على واتساب حقيقي، ٣ مرات على الأقل:**

```
١. زبون جديد بيبعت "مرحبا"  →  ترحيب + القائمة
٢. بيتصفح تصنيف            →  الأصناف
٣. بيضيف صنفين             →  السلة بتتحدّث
٤. بيراجع السلة            →  الملخص والمجموع
٥. بيختار استلام           →  خيارات الدفع
٦. بيختار كاش              →  🔴 الطلب بينشأ + تأكيد
٧. اللوحة                  →  الطلب ظهر خلال ٥ ثواني
٨. الموظف بيقبل            →  الحالة تحدّثت + انسجلت بالخط الزمني
٩. قيد التحضير → مكتمل     →  payment_status صار collected
١٠. **نفس الزبون بيبعت "مرحبا" تاني**  →  🔴 اقتراح طلبه المعتاد
```

**سجّلوا:**
- ⏱️ الزمن من أول رسالة لإنشاء الطلب (**الهدف < ٣٠ ثانية للطلب المتكرر**)
- 📊 **عدد الرسائل الصادرة للطلب الواحد** ← الرقم اللي رح يحدد سعر الاشتراك
- 📹 فيديو للعرض على المرشد

## أخطر ثلاث مصايد بهالـSprint

**١. حساب توقيع الـwebhook على JSON معاد التسلسل بدل البايتات الخام.**
بيفشل **دايما**، والرسالة ما بتقول ليش. `rawBody: true` على المسار من أول سطر.

**٢. الخلط بين طبقتي منع التكرار.**
بوابة الحدث بتمسك **إعادة إرسال ميتا لنفس الرسالة**. الـCAS بتمسك **الزبون اللي ضغط مرتين**. هدول حدثين مختلفين تماما بمعرّفين مختلفين. **شيل أي وحدة، وبترجع ثغرة "طلب مكرر" من الباب التاني.**

**٣. نسيان `set_config` بمسار بالمحرك.**
الاستعلام **ما بيرمي خطأ** — بيرجّع **صفر صفوف**. فبتلاقي حالك بتدوّر على "ليش القائمة فاضية" وإنت مش شايف إن السبب سياق مفقود. **كل مسار بالمحرك بيمر من نفس الدالة اللي بتضبط السياق. بلا استثناء.**
